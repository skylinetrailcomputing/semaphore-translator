# Native-fixture verification contract

**Status:** FROZEN (Issue #20, Epic 3 — the true-lockstep gate for [3.3]/[3.4]).
**Machine-readable companion:** [`invariants.json`](invariants.json).
**Backs:** [`ADAPTER-CONTRACT.md` §7](../ADAPTER-CONTRACT.md) (verification),
§2 (coordinate frame), §3 (the two flips). Spec §3.2 / §4.2 / §7.

This document and `invariants.json` freeze the geometric assertions that **both**
platform adapters must satisfy on a set of known poses. It backs the JSON the
same way [`ALPHABET-VERIFICATION.md`](../ALPHABET-VERIFICATION.md) backs
`semaphore_alphabet.json`: the JSON is the terse machine contract, this is the
human reasoning it is written and reviewed against.

---

## 1. Why this exists (and why the parity harness isn't enough)

The parity harness ([#14](../test_vectors.json)) proves the two platforms agree
*downstream of the adapter* — but it **cannot catch a wrong flip**, because
`test_vectors.json` is defined as the adapter's **output** (post-mirror,
post-y-flip). Feed both platforms the same post-adapter keypoints and of course
they decode identically, whether or not either adapter's flips are correct.

The y-flip and horizontal mirror (`ADAPTER-CONTRACT.md` §3) are the only
genuinely new logic in Epic 3 and the entire risk surface. The only way to
verify them is to run the **real native pose estimator** on a **known pose** and
assert the adapter's output lands in the right place. This contract freezes
*what* "the right place" means, so iOS and Android assert the **same** thing —
the same discipline that froze the alphabet against one canonical chart.

## 2. The two reference frames (don't conflate them)

| | Frame | Origin / axes |
|---|---|---|
| **Pose image** (`pose_*.png`) | observer / camera view | image pixels, y-down; signer faces the camera |
| **`invariants.json`** + `reference_post_adapter` | post-adapter, signer's perspective | normalized `[0,1]`, **+x = signer's right**, **y-up** |

These two frames are related by exactly the adapter's mirror + y-flip — which is
the whole point. **In the image, the signer's right arm appears on the
observer's left** (they face you), so the `right_arm_out` figure extends its arm
toward the *left* edge; after a correct adapter, that same arm has
`right_wrist.x > right_shoulder.x` in the signer's frame. If the image and the
`reference_post_adapter` numbers seem mirror-flipped, that's correct — and is
exactly the transform the invariants pin.

## 3. The canonical poses

Both images are **3D-rendered humans** generated by
[`../tools/gen_native_fixtures.py`](../tools/gen_native_fixtures.py) (a Blender +
MPFB script; see §6 for why a real-ish human is required). The figure is posed via
its rig to depict each pose in the observer's view. The image is deliberately
**not** pixel-matched to `reference_post_adapter` — it doesn't need to be: the
invariants are **relational** (§4), so any image that *depicts* the pose satisfies
the same contract, and the real estimator's coordinates (which differ from the
synthetic reference) still pass. Regenerate with
`blender --background --python shared/tools/gen_native_fixtures.py`.

### `right_arm_out` — the discriminating pose
Signer's **right arm straight out** to the signer's right (position id 2, 0°);
**left arm straight down** (position id 0, −90°). Asymmetric **on purpose**: only
an asymmetric pose distinguishes a wrong horizontal mirror from a left/right
anatomical-label swap (`ADAPTER-CONTRACT.md` §3b) — a symmetric pose looks
identical under either bug.

| Invariant | Pins | Reading |
|---|---|---|
| `right_wrist.x > right_shoulder.x` | horizontal mirror | id 2 points along +x; a missed/extra mirror flips it to lesser x |
| `\|right_wrist.y − right_shoulder.y\| < 0.15` | y-flip | id 2 is horizontal; a wrong y-flip tilts the out-arm |
| `left_wrist.y < left_shoulder.y` | y-flip | id 0 points down ⇒ wrist below shoulder in y-up; a wrong y-flip inverts it |
| `right_shoulder.x > left_shoulder.x` | mirror / labels | signer faces camera, +x = signer's right ⇒ right shoulder at greater x |

### `arms_down` — the symmetric sanity pose
Both arms straight down (id 0 / id 0). Pins the y-flip independently on each arm
(`{left,right}_wrist.y < {left,right}_shoulder.y`) and the mirror via shoulder
order (`right_shoulder.x > left_shoulder.x`).

## 4. The invariant DSL

Each invariant is a relation between two operands (`<keypoint>.<x|y>`, names from
`keypoint_contract.json.keypoints.names`):

- `gt` — `lhs > rhs`
- `lt` — `lhs < rhs`
- `abs_diff_lt` — `abs(lhs − rhs) < value`

Invariants are **relational on purpose**: they hold for *any* correct adapter
output regardless of exact coordinates, so the real estimator's numbers — which
vary run-to-run and differ between Vision and ML Kit — still satisfy them.
`reference_post_adapter` is a **synthetic** ideal output used only to self-test
the invariants and the decoder; it is **not** the expected estimator output.

## 5. How the two-layer fixtures use this (Epic 3)

Per the #3 grooming (Q2), each platform builds **two** fixture layers:

- **Layer 2 — calibration (one-time):** run the *real* estimator (iOS Vision on
  the simulator; Android ML Kit on a device/emulator — the repo's first
  `androidTest`) on these images, push the result through the adapter, and assert
  the invariants here. This is where the y-flip and mirror are pinned per
  platform. Not run per-commit.
- **Layer 1 — regression (per-commit):** the Layer-2 capture is recorded as a
  fixed **native skeleton** and replayed through the adapter in a fast unit test
  (iOS sim XCTest / Android local JVM, emulator-free), asserting the same
  invariants.

**Boundary — what is *not* in this ticket:** the recorded native skeleton is
**per-platform** (Vision joints ≠ ML Kit landmarks) and lands in each platform's
ticket ([#21]/[#22]), not here. This ticket is the **shared** contract: the
images, the invariants, and the (already-frozen) post-adapter expectations.

## 6. Image source & detectability caveat

The images are **3D-rendered humans** (MPFB / MakeHuman assets, **CC0** —
license-clean for an OSS repo, reproducible from the committed generator). This was
forced by the Layer-2 calibration (verified 2026-06-20 during #21): Apple Vision
returns **zero** faces/bodies/humans on a flat 2D figure — even a carefully shaded
one — because pose estimators are trained on real people and key on 3D **form**,
not texture. A rigged 3D human, **even untextured**, is detected with all six
keypoints above the `MIN_KEYPOINT_CONFIDENCE` floor, because its base mesh carries
real facial/limb geometry (a *featureless* mannequin, by contrast, makes Vision
flip the L/R labels — §3b — so the mesh's face matters). The figure is **dressed**
in CC0 clothing (a t-shirt + trousers, Issue #27) for a nicer public-repo asset;
detection still clears the floor on all six keypoints with correct L/R labels
(re-verified after dressing). If an estimator still can't read an image, **swap in
a real photo of the same pose** — the invariants are relational and image-agnostic,
so the contract (this file + `invariants.json`) is unaffected by the swap.

The recorded iOS skeleton in `vision_skeletons.json` is captured from these
committed images by the host tool
[`../../ios/Tools/extract_vision_skeleton.swift`](../../ios/Tools/extract_vision_skeleton.swift)
(`swift ios/Tools/extract_vision_skeleton.swift <image>`); re-run it after
regenerating the fixtures and paste the result back. Body pose runs on the macOS
host, not the iOS Simulator — hence a host tool rather than a simulator test.

> **Platform note — Apple Vision body pose does not run on the iOS Simulator**
> (`VNDetectHumanBodyPoseRequest` → "unable to setup request"). iOS Layer-2
> calibration was captured from the **macOS host** Vision (identical framework and
> lower-left-origin convention) and frozen into the per-platform recorded skeleton
> (`ios/Tests/Fixtures/vision_skeletons.json`, consumed by the camera-free Layer-1
> test). The live `VisionCalibrationTests` skips on the simulator and runs on a
> real device. (Android's ML Kit Layer-2 likewise wants a device/emulator.)

**Flags don't affect decode.** Classification is on the shoulder→wrist arm
vector, and a correctly held flag is a collinear extension of the arm, so it
lands in the same octant; the Epic-5 classifier consumes the 12 keypoint floats
(`keypoint_contract.json.model_input_order`), never pixels, so it is invariant to
flag presence/type/colour by construction. Flags matter only one stage upstream,
at pose **detection**: a large flag can occlude a wrist/elbow or perturb wrist
localization → lower confidence (→ indeterminate via `MIN_KEYPOINT_CONFIDENCE`)
or a small angle nudge (absorbed by `ANGLE_TOLERANCE_DEG`). That is a Layer-2
detection-robustness question, not a contract one — so Layer-2 imagery in
[#21]/[#22] should include **both flags-in-hand and empty-hand** signers (and a
couple of flag sizes/colours), which is a further reason that imagery wants real
photos. The deeper geometric ambiguity is a **bent arm** (shoulder→wrist stops
representing the intended direction), independent of flags; the carried-but-
non-gating `elbow` keypoint is the lever there, not flag tracking.

## 7. How both test suites consume it

`invariants.json` is loaded by the iOS (`NativeFixtureTests`) and Android
(`NativeFixtureTest`) suites today. Until the per-platform adapters exist
(Epic 3), those tests prove the contract is well-formed and *has teeth*: for each
pose they assert `reference_post_adapter` satisfies every invariant and decodes
(via `SemaphoreDecoder`) to `expected_position_ids`, then assert that a
mirror-broken and a y-flip-broken variant each violate at least one invariant.
[#21]/[#22] add the Layer-1/Layer-2 cases that feed real adapter output through
the same invariants.
